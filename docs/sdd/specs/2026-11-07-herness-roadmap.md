# herness Spec roadmap

**Classification:** architectural / multi-spec

**Status:** 分割・依存関係、H1〜H3のspec、H1/H2の接続追加契約は承認済み。H1・H2の実装はmainへ統合済みだが受入未完了。H3は承認済み契約に基づくplanを作成する段階であり、未実装。追加の本実装・実接続の許可ではない。

## 全体目標

Piを出発点に、SDDによる開発を進めるデスクトップ型エージェントハーネス「herness」を作る。最初の対象はmacOSとする。軽さを重視してTauriとRust中心の構成を優先し、PiのRust移植や他のエージェント基盤もH1で比較する。CLIの操作をGUIに置き換えるだけでなく、子エージェントの起動・継続・完了判定をhernessが制御する。

SDDの正本は既存の`../sdd`とする。成果物・検証・承認の契約を再利用し、herness固有の責務移管をSDD側の連携定義に明記する。他ホスト向けの既存動作は変えない。このロードマップは分割と所有者を定めるもので、APIや状態遷移の正本にはしない。

## 合意済みの要求

- hernessはデスクトップアプリとして作り、macOSから対応する。
- 基盤はTauriとRust中心を優先する。重要な機能差・保守性で不利な場合は、理由を確認してNode sidecarも代替案として検討する。PiのTypeScript SDK利用は固定要件としない。
- 実行モデルの認証にはOpenAI・Anthropic・OpenAI互換接続先のAPIキーとChatGPTログインが必要。実アカウントでのログイン・送信を伴う確認は、別途利用者の許可を得て行う。
- `../sdd`で定められたskillsを利用する。herness連携のためのSDD側の追加は、今後の設計・実装範囲に含めてよい。
- SDDの対象Markdownを作成・編集したら、親モデルが呼び出しの要否を判断せず、hernessがHTMLを作成・編集する子エージェントを起動する。開いているプロジェクト内の外部エディタ・シェルによる変更も検知対象に含める。
- HTMLはMarkdownの見た目を写すだけでなく、人間の認知負荷を下げるために順序の変更、図解・グラフ、要約の追加を使えるものとする。元の情報はHTML内にすべて保持し、要件・条件・例外の意味を変えたり、根拠のない関係・数値を追加したりしない。HTMLの品質・完了判定にもH2の共通機構を使い、軽量LLMやDecisionモデルを選べるようにする。
- ファイル作成・編集のツール引数に短い「変更理由」を追加し、対象の変更・実行結果と関連付けて記録する。チャットとは別の画面から確認できるようにする。
- 変更理由の必須化は作成・編集ツールに適用する。シェルはコマンド単位の目的・結果を記録し、外部編集に理由を推測して付けない。
- 初期対象は信頼するコードを扱う利用とし、OSによるエージェントの強制隔離は初期要件にしない。ウィンドウを閉じてもアプリが起動している間は実行を継続し、明示的なアプリ終了では安全に停止・保存して次回再開できるようにする。
- シェル利用は基本的に実行開始時に許可する。設定済み権限に従うモードと、軽量LLM・Decisionモデルで操作の可否を自動判定するモードを切り替えられるようにする。どちらも明示的な禁止・人間確認の設定を優先し、モデルの判定失敗・判定不能では実行せず確認待ちにする。
- sdd-executeのTask用エージェントは、親モデルではなくhernessが起動する。
- 各子エージェントは未完了なら継続する。ただし人間の判断待ち、進展なし、回復不能、設定した費用・時間等の上限では、完了扱いにせず停止する。
- 完了判定には通常のLLMだけでなく、JevやOpenAI Decisions APIのDecisionモデルを選べるようにする。

## 全体の観測可能な完成条件

1. macOSでデスクトップアプリを起動し、ローカルのプロジェクトを開いて、H1で選定したエージェント基盤とSDDの開発フローを利用できる。
2. ファイルの作成・編集に渡した変更理由と、その変更の成否・対象を、別画面で追跡できる。モデルの内部思考を取得したものとは表示しない。
3. 対象Markdownをherness内外から編集すると、親モデルの追加のtool callなしでHTML用エージェントが起動する。全文情報を保持しつつ、順序の変更や適切な図解・グラフによって理解を助けるHTMLを作れる。最新のMarkdownへの対応、安全性、情報保持と表現の品質を検証・判定し、未同期・失敗・判定不能を明示する。
4. 利用者が承認したplanの実行を開始すると、hernessがTask用エージェントを順番に起動し、未完了なら合意済みの範囲で継続する。親モデルによるdispatchを必要としない。
5. 通常LLM・Jev・OpenAI Decisions APIを完了判定の選択肢として利用でき、HTMLの品質・完了判定にも軽量LLMやDecisionモデルを利用できる。必須検証の失敗、古い証拠、判定APIの失敗を成功として処理しない。
6. 実行状況・停止理由・判定の証拠を確認でき、人間の承認が必要な状態から無断で先へ進まない。完了判定だけでpush・merge・公開を実施しない。
7. 設定権限モードと自動判定モードを切り替えられる。自動モードでも明示的な禁止・人間確認を迂回せず、判定失敗・判定不能では操作が実行されない。

これらは製品全体の完成条件であり、この文書への承認だけでは実装を許可しない。個別specの受入条件と検証方法は、それぞれの所有specで具体化する。

## 初期範囲外の提案

- CLI製品の提供、およびWindows・Linux対応を初期完成条件に含めること。
- リモート実行、複数利用者による共同作業、クラウド同期。
- SDDのMarkdownを正本とする方針やTargetの範囲を変えること、共通validatorをherness独自の検証に置き換えること。H3で共通policyに再構成向けの検証契約を追加することは範囲内とする。
- 機械的なMarkdown-to-HTML rendererによるHTML作成。HTMLは起動されたエージェントが別途著作する。
- 実装Taskの並列実行、Taskごとのworktree作成、必須の独立レビューループを初期要件に加えること。
- 判定モデルの回答による権限拡大、検証の迂回、無制限・無停止の実行。

これらの範囲外項目はロードマップの提案に含まれる。将来の拡張を禁止するものではない。

## Specの分割

H1〜H3は承認済みのspecを保存した。H4・H5は未作成の予定specであり、プレースホルダーのファイルは作らない。実際のspecを保存した時点で、この一覧にパスを追記する。

### H1 — 実行基盤と変更理由の記録

- **目的・境界:** TauriとRustを優先した基盤選定、エージェントの実行境界、プロジェクトとセッション、子エージェントのライフサイクル、ツールの権限境界と許可モード、ファイル作成・編集と変更理由の記録を定める。SDD packの参照・対応範囲と、デスクトップから利用するホスト境界もここで定める。
- **所有するもの:** エージェント実行・tool実行・変更記録の識別とイベント、変更理由の入力と記録、停止要求と実行結果、設定権限モードと自動判定モードの適用・優先規則。自動判定の評価器を接続する境界はH1で定め、共通のモデル接続実装はH2で追加する。
- **含めないもの:** 完了まで繰り返す規則、HTML同期、Taskの順序制御、完成版の画面レイアウト。
- **観測可能な完了:** UIから利用可能な境界を通じて選定した基盤の実行・停止ができ、ファイル作成・編集の変更理由と実行結果を関連付けて取得できる。設定権限モードと自動判定の接続境界、権限と子エージェントの分離、終了と復旧について保証する範囲がテストで確認されている。実モデルによる自動判定はH2に依存し、利用できない評価器を許可扱いで代替しない。
- **消費先:** H2・H3・H4・H5。
- **Spec:** [H1: 実行基盤と変更理由の記録](2026-11-07-h1-runtime-design.md)。2026-11-08に承認済み。
- **Plan:** [H1 Runtime and Audit Implementation Plan](../plans/2026-11-08-h1-runtime.md)。実装はmainへ統合済み。[受入記録](../../research/2026-11-08-h1-acceptance.md)ではOpenAI・Anthropic APIキー経路が未確認で、H1受入は未完了。

### H2 — 継続実行と完了判定

- **目的・境界:** 共通の子エージェント監督機構を定める。完了条件・検証証拠から、継続・完了・人間待ち・失敗等を扱い、軽量モデルを含む通常LLM・Jev・OpenAI Decisions APIを接続する。H3のHTML評価にも利用し、H1で定める自動許可判定の接続境界にモデル実装を提供する。
- **所有するもの:** 完了判定への証拠入力と判定結果、必須検証との関係、継続・停滞・予算・判定不能時の規則。モデルの確率と、hernessが行う状態遷移は区別する。
- **含めないもの:** SDD planの解釈、Taskの進行台帳、HTML固有の検証・公開手順、H1の権限規則の再定義。操作の許可判定とタスクの完了判定は別の問いとして扱い、モデルで明示的な禁止・人間確認を上書きしない。
- **観測可能な完了:** 同じ完了条件に対し3種類の判定方式を選べ、未完了の子エージェントが継続する。必須検証の失敗、判定不能、安全停止、上限到達では完了に遷移しないことを確認できる。
- **消費先:** H1の自動判定用接続境界・H3・H4・H5。
- **Spec:** [H2: 継続実行と完了判定](2026-11-08-h2-supervision-design.md)。2026-11-08に承認済み。H1の継続・評価器引継ぎ等の追加契約もH1正本でレビュー・承認済み。未確認経路は未確認のまま保持する。
- **Plan:** [H2 Supervision and Assessment Implementation Plan](../plans/2026-11-08-h2-supervision.md)。実装をmainへ統合済み。[受入記録](../../research/2026-11-08-h2-acceptance.md)ではPhase AとCommand Code経由の限定的なJev実接続を確認したが、通常LLM・Decisions等は未確認でTask 18とH2全体は未完了。

### H3 — HTML companionの自動更新と視覚的再構成

- **目的・境界:** Target Markdownの変更検知から、hernessによるHTML用エージェントの起動、検証済みcompanionの反映までを定める。人間の認知負荷を下げるため、原文の全文情報と意味を保持しつつ、順序の変更、図解・グラフ、要約の追加による再構成を認める。外部編集、連続編集、実行中の原文変更、再試行、自己誘発ループも扱う。
- **所有するもの:** HTML同期ジョブ、原文の版とcompanionの対応、同期の成功・保留・失敗の通知、視覚的再構成と情報保持の契約、図解・グラフの根拠と評価証拠。HTML著作をhernessへ移す連携差分と、SDD共通policyに追加する再構成向けの検証契約も所有する。品質・完了の判定にはH2を利用し、軽量LLMやDecisionモデルを選択できるようにする。
- **含めないもの:** Markdown正本・Target判定・digest・安全性の迂回、情報の欠落・意味の改変・根拠のない情報追加、Task全体の完了判定、汎用の文書変換サービス。
- **観測可能な完了:** hernessのツール編集と外部編集のどちらからも自動起動し、最新の原文に対応するHTMLだけを同期済みと扱う。順序変更や図解を含む代表文書で全文情報の保持と理解のしやすさを確認し、対応する共通policyの必須検証とH2経由の評価が成立する。古い結果、危険なHTML、情報欠落、判定不能を成功として公開せず、既存成果物を壊さない失敗経路を確認できる。
- **消費先:** H4・H5。
- **Spec:** [H3: HTML companionの自動更新と視覚的再構成](2026-11-09-h3-html-sync-design.md)。2026-11-09にH3 specと各正本のH1/H2接続追加契約を承認済み。追加部分は未実装。

### H4 — herness主導のsdd-execute

- **目的・境界:** 承認済みplanの取込み、Task単位の子エージェント起動、文脈の引継ぎ、進行記録と完了への遷移をhernessが制御する。H2の継続実行を利用し、H3の同期状況を必要な完了条件に反映する。
- **所有するもの:** planとTaskの対応、Taskの順序・進行台帳、制約・正本specの伝達、再開とplan変更の扱い、親モデルのdispatchと再開回数を置き換えるSDD連携差分。
- **含めないもの:** 共通の判定モデルAPI、HTML著作手順の再定義、未承認のspec・plan変更、完了に伴う自動push・merge・公開。
- **観測可能な完了:** 親モデルがsubagent toolを呼ばなくてもTaskが順番に実行され、Global Constraintsと正本specが引き継がれる。停止・再開・未完了を追跡でき、必要な検証やHTML同期が不成立なら先へ進まない。
- **消費先:** H5。予定spec、パス未作成。

### H5 — デスクトップ操作とmacOS配布

- **目的・境界:** プロジェクトと会話、別画面の変更理由、子エージェント・Taskの進行、HTML同期、判定方式の設定、人間の承認と停止・再開を操作できる画面、およびmacOSでの導入方法を定める。
- **所有するもの:** 利用者の操作、表示、ナビゲーション、アクセシビリティ、配布時の操作要件。実行や同期の状態はH1〜H4を正本とし、UIだけの独立した成功状態を作らない。
- **含めないもの:** 実行・完了・権限のバックエンド契約の再定義、他OS向けの配布。
- **観測可能な完了:** macOS上のデスクトップアプリで全体の完成条件を通して確認できる。変更理由をチャット以外から閲覧でき、未同期・判定不能・停止状態を成功と見誤らず、人間が必要な操作を行える。
- **消費先:** 利用者。予定spec、パス未作成。

## 依存関係と設計順序

必須の依存関係は次のとおりとする。

- H2はH1に依存する。実行・停止・証拠の識別境界がなければ、継続と判定を定義できない。H1は自動許可判定の接続境界までを先に定め、H2がモデル実装を提供するため、H1の設計・実装を未作成のH2の契約には依存させない。
- H3はH1・H2に依存する。HTML用エージェントにも共通の実行・継続・停止を適用し、情報保持や視覚的再構成の品質・完了判定にもH2を利用するため。
- H4はH1・H2・H3に依存する。Task実行には共通監督機構が必要であり、対象文書を変更するTaskの完了はHTML同期と整合しなければならないため。
- H5の依存する操作の詳細設計は、その操作が利用するH1〜H4の契約確定後に行う。見た目の検討や試作まで禁止するものではない。

承認済みの設計順序はH1 → H2 → H3 → H4 → H5とする。これは個別specを自動で連続設計・実装する指示ではない。UIの実装を最後まで禁止せず、必要最小限の接続確認は各specの受入条件で扱う。

**現在の対象は、承認済みH3のsdd-planである。** H1・H2は実装を統合済みだが受入未完了。H3が必要とする追加・補修はH3 specと各正本の追加契約に記録し、既存コードで利用可能とはみなさない。H3のplan保存と実装指示までは本実装を始めず、実接続には別途許可を必要とする。H4以降へは自動で進まない。5つのspecの分割・順序・契約所有者は変更しない。

## 共通契約の所有者

- **SDD pack:** Targetの範囲、Markdown正本、HTMLの別著作・digest・共通validator、既存のplan・Task・成果物契約。H1・H3・H4が参照する。herness固有の変更は、それを所有するspecで適用範囲を明記する。H3で必要となる再構成向けの検証も共通policy側に追加し、他ホストの既存動作を維持する。
- **H1:** 選定したエージェントの実行境界、toolと変更理由の記録、許可モードとその評価器の接続境界、基本の権限・停止・イベント。H2〜H5が参照する。
- **H2:** 共通のモデル接続、証拠と完了判定、継続・停止の共通規則。H1の接続境界に自動許可判定のモデル実装を提供し、H3〜H5が参照する。
- **H3:** HTML同期の版・結果・失敗、全文情報を保持する視覚的再構成とその評価契約。H4・H5が参照する。
- **H4:** Task進行とSDD実行フロー。H5が参照する。
- **H5:** 画面上の操作と表示。上流の共有契約に変更が必要なら、正本の所有specを先に更新する。

## 未解決事項と解消時点

- **デスクトップ技術とエージェント基盤:** H1の承認でTauri＋pi-rustの埋め込み境界を採用した。詳細と固定する検証基準はH1を正本とする。既存Piの全機能互換や製品の軽量性を未検証のまま保証せず、移植やforkを既定の作業にはしない。
- **基盤候補の実証:** 承認された最大45分の使い捨てspikeでは、Tauriとネイティブpi-rustの接続、独自ツール、停止・保存・復元を確認した。[結果と未確認範囲](../../research/2026-11-07-pi-rust-spike.md)をH1の設計証拠とする。実ログイン・外部モデル送信・有料API呼び出し・本実装は行っていない。Rust製であることだけで軽さ・安定性・Pi互換を保証しない。
- **権限・隔離・秘密情報:** 信頼するコード向けとし、OSによる強制隔離は初期要件にしないこと、許可モードの切替、明示的な禁止・人間確認の優先、モデル判定失敗時に実行しないことは合意済み。シェル、拡張、MCP等を含む具体的な利用経路、モード切替の適用単位、モデルへの送信範囲・資格情報の保存はH1で決める。変更理由の記録やモデル判定をOS sandboxの代わりにはしない。
- **保存と復旧:** ウィンドウ閉鎖では継続し、アプリ終了では停止・保存して次回再開できることは合意済み。クラッシュや停止途中のセッション、変更記録、ジョブの扱いはH1で定め、各所有specが従う。停止した処理の再実行を無条件に許可したものとは扱わない。
- **判定と継続の具体的規則:** 完了条件の作成・承認、証拠の鮮度、判定モデルの選択単位、閾値、予算の数値、停滞検知、API失敗時のfallbackはH2で決める。未定のまま無制限継続や成功扱いを実装しない。
- **HTML同期の失敗と競合:** 失敗時にどの作業まで止めるか、外部からHTMLが編集された場合、移動・削除・bootstrapの扱いはH3で決める。破壊的操作を含める場合は、その可逆性・失敗・再実行の結果を実装前に明示的に確認する。
- **H3面談での解消:** project単位で有効化し、同期失敗時は通常作業を続けて必要な完了だけ保留する。意味を保つ言い換え、履歴付きの自動反映、外部HTML競合での人間待ち、削除・移動時の旧成果物保持を合意した。意味評価はH2、offline CIは静的検証・証跡整合を担当する。詳細と残る有効化前検証は承認済みH3 specを正本とする。
- **HTML再構成の検証と評価:** 現行SDDは原文の見出し・本文の順序保持を要求し、要約追加や再構成を認めていない。H3で、全文情報と意味の保持、図・グラフの根拠、認知負荷を下げる表現の評価方法、軽量LLM・Decisionモデルへ渡す証拠、共通policyとCIでの検証方法を定める。静的・安全な閲覧と鮮度の検証は維持し、意味や視覚表現の品質をdigest一致だけで保証したとは扱わない。このロードマップのHTMLには、まだ変更していない現行の検証契約を適用する。
- **planの機械的取込みとGit連携:** 現行planには完了条件等の散文があり、既存スクリプトだけでは実行契約が完結しない。取込み形式、変更時の再承認、worktree選択、commit境界、sdd-finishとの互換範囲をH4で決める。曖昧なplanを黙って解釈して実行しない。
- **配布と製品UI:** macOSの最低対応版、署名・notarization・更新方式、画面構成は、H1の技術境界に影響する項目をH1で先に確認し、残りをH5で決める。
